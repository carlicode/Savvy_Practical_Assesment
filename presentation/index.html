    09 · What went wrong

    Six problems I hit, and how I fixed them

    Nothing here was hidden by a lucky run. Each problem was caught by reviewing the real output.

    01

    Everything looked urgent

    Problem
    11 of 19 leads came back High.
    Cause
    A vague rule: "High = urgent or ready to act".
    Fix
    Clear criteria: High means ASAP, funds ready or a tour this week.
    Lesson
    If everything is urgent, nothing is.
    02

    The AI could see the answers

    Problem
    Manual notes like "Ambiguous intent" were reaching the model.
    Cause
    Payload built as "everything except PII" (a block-list).
    Fix
    An allow-list: the AI gets only the fields it needs.
    Lesson
    Test with what production will really have.
    03

    A privacy fix created a bug

    Problem
    4 leads got "Find contact info" though they had an email. One draft asked for an email we already had.
    Cause
    Without contact data, the model guessed the channel.
    Fix
    Code computes the channel and sends only a label: email, text or none.
    Lesson
    Hide the data, not the fact the AI needs.
    04

    A rule the AI didn't always follow

    Problem
    An unclear lead came back as Medium priority.
    Cause
    Prompts guide the model; they don't guarantee it.
    Fix
    "Unclear = Low" is now enforced in code.
    Lesson
    If a rule must always hold, it belongs in code.
    05

    Same lead, different answer

    Problem
    SAV-1016 was High in one run and Medium in the next.
    Cause
    LLM output varies slightly even at temperature 0.
    Fix
    Every run is logged. Documented as the main limitation.
    Lesson
    Measure, don't assume.
    06

    The environment fought back

    Problem
    Installs were blocked, and one run used an unsaved file.
    Cause
    System Python is externally managed (PEP 668).
    Fix
    An isolated virtual environment and pinned versions.
    Lesson
    Reproducibility starts with the setup.
    10 · Security & privacy

    Safe by design, not by luck

    Real client data would flow through a system like this, so I treated the fictional data as if it were real.

    No personal data to the AI

    Names, emails, phones and IDs never leave the machine. The model gets a short allow-list of business fields.

    Secrets never in code

    The API key lives in a git-ignored .env. The template is empty, and files were scanned for keys before the first commit.

    Safe to share

    The repo is public for review, with no secrets and only fictional data. On S3, a bucket policy opens one CSV for read-only access, and nothing else.

    Nothing is sent automatically

    Follow-ups are drafts for a person to approve. No emails or texts go out.

    Fails safe

    If the AI fails or returns something invalid, the lead goes to a person. The run never stops halfway.

    No live AI on the web

    This page shows pre-computed results, so there's no key in the browser and nobody can run up costs.

    rationale: str

    def needs_human_review(row, result):
    return (
        result.intent == "Unclear"
        or "lead_type_unclear" in flags
        or row["possible_duplicate_of"]
        or both_contacts_missing(row)
        or result.confidence < 0.7
        or result.risk_or_contradiction  # the only AI-judged rule
    )

    13 · What if it scales?

    Built for a sample, designed to grow

    Some choices are right for 20 fictional leads and wrong for 20,000 real ones. Here's what I'd change, and why.

    Today (prototype)Why it's fine for 20 leadsAt scale
    CSV loaded by handSample data, one batchCRM webhook (e.g. GoHighLevel): each lead triaged the moment it arrives
    One AI call per lead, in sequence19 calls take secondsParallel calls with retries and back-off; Batch API for backfills
    Exact duplicate match in memoryOne obvious duplicateDatabase plus fuzzy matching, and checks against leads already in the CRM
    Console, text logs, CSVEasy to inspectDatabase plus a live dashboard
    API key in a local .envLocal and simpleAWS Secrets Manager with rotation
    Review threshold at 0.7Better to over-reviewTuned with real outcomes so reviewers aren't flooded
    AI variability checked by eyeA handful of runs, reviewed manuallyLabeled evaluation set, accuracy tracked on every change
    Cost computed at the endAlready tracks tokensBudget alerts in CloudWatch
    3,000 What breaks first is people, not cost. At today's 30% review rate, 10,000 leads a month means 3,000 manual reviews. Tuning the review rules with real data matters more than AI spend, which would be about $1.53.

    15 · Limitations & next steps

    What I'd do next

    Main limitation: the AI's priority can shift between runs for the same lead. The fix is to let code score the timeline and the AI read only the notes.

    1

    Connect the CRM

    Triage each lead as it arrives (e.g. a GoHighLevel webhook) and write the result back to the record.

    2

    Make priority consistent

    Timeline scoring in code, plus a labeled set of leads to measure accuracy on every change.

    3

    Learn from the team

    When a rep changes a priority, log it. Those corrections become the accuracy metric and improve the rules.

    How I'd measure success
    Time to first contact on High leads% of AI suggestions accepted unchangedHuman review rateCost per leadDuplicate contacts avoided
